## Client outcomes

- `leakage`: Reduce defect leakage into UAT and production
- `speed`: Faster, more predictable releases
- `cost`: Lower cost of quality
- `automation`: Increase test automation coverage
- `uat`: Reduce business effort in UAT
- `compliance`: Regulatory and data privacy compliance
- `visibility`: Better quality visibility and reporting
- `aicap`: Build the client's own AI capability in QA
- `aidlc`: Adopt AI-DLC / AI-augmented delivery

## QA practice categories

### Test management

#### Strategy, governance and operating model

Linked outcomes: leakage, uat, visibility

| Practice | Level 1 | Level 3 | Level 5 | Recommendation | Effort |
|---|---|---|---|---|---|
| QA strategy and test policy | No documented strategy; testing is ad hoc per project | Strategy documented per program but applied inconsistently | Enterprise QE strategy, risk-based, reviewed every quarter or PI | Publish a risk-based QE strategy and test policy aligned to the release cadence | Low |
| Independent QA and clear roles | Developers test their own code; business UAT is the only gate | Dedicated QA in some teams; roles and accountability unclear | QE embedded in every squad with defined roles (QE lead, SDET, AI-QE champion) and a RACI | Define QE roles and RACI; embed QA in the highest-risk squads first | Medium |
| Quality gates and Definition of Done | No entry or exit criteria; go-live decided on judgement | Gates exist at UAT or release, partly enforced | Story, sprint and release gates with QA criteria in DoR/DoD, enforced and partly automated | Add QA criteria to DoR/DoD and introduce a release go/no-go checklist | Low |
| Quality governance cadence | No regular quality reviews | Periodic status reporting without decisions | Regular quality council with leadership; decisions driven by metrics | Set up a monthly quality council and a sprint-level quality review | Low |

#### Requirements and test design

Linked outcomes: leakage, uat, speed

| Practice | Level 1 | Level 3 | Level 5 | Recommendation | Effort |
|---|---|---|---|---|---|
| Requirement testability | Stories often lack acceptance criteria | Acceptance criteria exist but vary in quality; QA joins late | Three-amigos refinement; testable Given/When/Then criteria before sprint start | Run three-amigos refinement and an acceptance-criteria quality checklist | Low |
| Test design and traceability | Tests written from memory; no traceability | Tests linked to stories; some design techniques used | Risk-based design with full requirement → test → defect traceability and measured coverage | Adopt risk-based test design with requirement-to-test traceability in Jira | Medium |
| Regression suite | No maintained regression suite | Regression suite exists but is outdated or bloated | Prioritized, risk-based regression pack maintained every sprint | Baseline and prioritize the regression pack, critical customer journeys first | Medium |
| Non-functional testing | Performance, security and accessibility not tested | Tested ad hoc before major releases | NFRs defined per story and tested continuously | Define NFR acceptance criteria and add baseline performance, security and accessibility checks | High |

#### Test execution and defect management

Linked outcomes: leakage, uat, speed

| Practice | Level 1 | Level 3 | Level 5 | Recommendation | Effort |
|---|---|---|---|---|---|
| In-sprint testing | Testing happens after development, often in UAT | Most stories tested in sprint; spillover is common | Stories tested and closed within the sprint; test-first where possible | Shift testing into the sprint and track QA-ready vs QA-complete per story | Medium |
| Test management tool usage | Spreadsheets or no tool | Tool in place (Zephyr, Xray, ADO) but data is inconsistent | Tool is the single source of truth with execution history and traceability | Standardize test management in Jira (Zephyr or Xray) with templates and conventions | Low |
| Defect lifecycle and triage | No defined workflow; severity means different things to different people | Workflow defined; triage irregular and defects age | Daily triage, severity SLAs, root-cause analysis feeding prevention | Define the defect workflow, severity SLAs and a daily triage routine | Low |
| UAT effectiveness | Business finds most defects in UAT | UAT still finds functional defects QA missed | UAT focuses on business validation; few defects found there | Add system and end-to-end QA before UAT using business-approved scenarios | Medium |

#### Test automation and CI/CD

Linked outcomes: automation, speed, cost

| Practice | Level 1 | Level 3 | Level 5 | Recommendation | Effort |
|---|---|---|---|---|---|
| Regression automation coverage | Under 10% of regression automated | 30–60% automated, mostly UI | Over 80% automated across unit, API and UI layers | Automate critical regression journeys first, API before UI | High |
| Framework and test pyramid | No framework; record-and-playback scripts | Framework exists; UI-heavy and flaky | Maintainable framework following the test pyramid; flaky rate tracked under 2% | Stand up a standard framework (for example Playwright + BDD) with coding standards | Medium |
| CI/CD integration | Tests run manually on a tester's machine | Some suites run in the pipeline on a schedule | Tests run on every commit or PR; quality gates block bad builds | Wire automated suites into CI/CD with pass-rate quality gates | Medium |
| Automation maintenance | Scripts break every release; no owner | Maintenance is reactive | Failure triage, self-healing locators and maintenance budgeted every sprint | Assign maintenance ownership, add failure triage and pilot self-healing | Medium |

### Test data management

#### Test data management

Linked outcomes: compliance, speed

| Practice | Level 1 | Level 3 | Level 5 | Recommendation | Effort |
|---|---|---|---|---|---|
| Data provisioning | Testers create or request data manually; waits of days | Scripts or request forms for common data; some reuse | Self-service, on-demand provisioning integrated with pipelines | Build a test data catalogue and request process for common scenarios | Medium |
| Synthetic and masked data | Unmasked production copies in test | Masking applied in some environments | Synthetic or masked data by default; no raw PII outside production | Mask production-derived data and start synthetic generation for key entities | High |
| Refresh and integrity | Data is stale or corrupted; tests fail because of data | Periodic refreshes with manual fixes | Automated refresh, versioned data sets, reset per test run | Schedule refreshes and create resettable baseline data sets | Medium |
| Privacy and compliance | No controls over test data privacy | Policies exist but are not audited | Data classification, access control and audit trail aligned to regulation (PIPEDA, OSFI, GDPR) | Classify test data and align handling with privacy regulation | Medium |

### Test environment management

#### Test environment management

Linked outcomes: speed, cost

| Practice | Level 1 | Level 3 | Level 5 | Recommendation | Effort |
|---|---|---|---|---|---|

### Foundations

#### Agile and AI-DLC integration

Linked outcomes: speed, aidlc, leakage

| Practice | Level 1 | Level 3 | Level 5 | Recommendation | Effort |
|---|---|---|---|---|---|
| QA in Agile ceremonies | QA not part of planning or refinement | QA attends some ceremonies | QA shapes refinement, estimation and sprint goals | Include QA in refinement and planning, with QA effort in estimates | Low |
| Shift-left and shift-right | Testing only at the end | Some unit tests and static checks by developers | Unit and contract tests, PR checks and production monitoring all feed quality | Add shift-left practices (unit/contract tests, PR checks) and production monitoring feedback | Medium |
| QA's role in AI-DLC | No awareness of AI-driven delivery | Teams experiment with AI coding; QA's role undefined | QA joins mob elaboration, validates AI-drafted work at defined gates; test standards encoded as steering files | Define QA's role in AI-DLC: validation gates, steering files, testing of AI-generated code | Medium |
| Testing AI-enabled features | AI/LLM features tested like deterministic code, or not at all | Some manual evaluation | Evaluation suites for accuracy, safety, bias and drift run continuously | Set up evaluation-based testing for AI features (golden sets, guardrail tests) | High |

## AI readiness questions

| Question | Level 1 | Level 3 | Level 5 |
|---|---|---|---|
| AI tool access for QA | No approved AI tools for QA | Some tools licensed for a few users | Enterprise AI tools licensed for all of QA |
| AI usage policy and guardrails | No policy, or AI use blocked | Policy exists; approved use cases unclear | Clear approved use cases, data rules and human review gates |
| AI access to delivery data | AI tools cannot see requirements, code or test data | Partial access (for example docs only) | AI connected to Jira, Confluence, repos and test tools with controls |
| Team AI skills | No AI skills in the team | A few champions | Broad proficiency across QA and delivery |
| Leadership sponsorship | No sponsor for AI in QA | Interest but no budget or targets | Funded sponsor with measurable targets |
| Toolchain integration readiness | Closed tools, no APIs | Some APIs available | Open APIs and pipelines ready for AI agents |
